# Chinese.zip: связанные словари и переносимый результат

Статус: исследование пользовательского архива и предложение расширения. Автоматическое объединение связанных баз и совместимый разбор перекрывающихся тегов **ещё не реализованы**. Текущие изменения интерфейса не меняют конвертацию.

## Проверено

Источник: `/Users/a_abramenko/Downloads/chinese.zip`, 2 051 173 байта, 12 ZIP-записей. Архив только читался; исходный файл и результаты пользователя не изменялись. Содержимое не добавляется в репозиторий.

| UniversalChRu.dsl.dz | Universal (Ch-Ru) | Основной китайско-русский словарь |

Остальные записи — каталог, `.ann` и `.bmp`. Уже существующий `prepare_source` правильно находит **три основных словаря** и присоединяет `_abrv` к Universal. При нескольких базах приложение уже предлагает выбор, включая запуск отдельных заданий для всех. Семантической проверки межсловарных зависимостей сейчас нет.

В PhoneticList найдены **28 173** ссылки вида `[ref dict="Universal (Ch-Ru)"]…[/ref]`. Все они явно направлены в другой словарь. Текущий `dsl/renderer.rs` читает `target`, но теряет `dict`; `pipeline/link_index.rs` затем ищет цель только среди ключей текущего результата. Поэтому сообщения об отсутствующих статьях здесь в основном ложные по отношению к полному пакету.

Точное сравнение исходных заголовков нашло 28 148 целей. После раскрытия вариантов заголовков штатной `expand_headwords` и нормализации штатной `mdx_sort_key` находятся **28 149**, остаются **24**. Это количество ссылок, не уникальных статей. Примеры оставшихся целей: `啊尔巴尼亚人`, `百分之百分之百`, `贼喊捉贼喊捉贼`. Нельзя автоматически подменять их похожими словами: отсутствие точного ключа требует отдельного сообщения и проверки содержимого источника.

## Дополнительный результат пробы ядра

Проверка выполнена отдельной временной программой в `.work/archive-analysis` через реальные `prepare_source`, `DslReader` и штатные правила заголовков. Это диагностическая проба, не код продукта.

- PhoneticList проходит чтение: 22 949 статей, 22 943 уникальных нормализованных ключа; дополнительные предупреждения появляются позднее при проверке ссылок.
- Universal останавливается с `invalid_markup`: «Неожиданное закрытие тега: [/i]», статья начинается на строке 4. В её теле есть перекрывающееся закрытие форматирования, например открытый `[i]`, внутри `[lang]`, затем `[/i]` перед `[/lang]`.
- PhraseBook также останавливается с `invalid_markup`, статья начинается на строке 307.

Это подтверждает ограничение текущего строгого стека тегов. Проба не утверждает, что весь словарь повреждён: нужно различать допустимые особенности DSL и ошибки исходной разметки. Необходим совместимый разбор форматирующих тегов с контролируемым восстановлением, сохранением текста и отчётом о реально восстановленных местах. Ошибки структуры статей, ссылок, путей и кодировки нельзя молча подавлять.

## Предлагаемая обработка пакета

Пользователь выбрал совместимость с разными читалками. Предлагается сохранять связанные базы в одном самостоятельном MDX/MDD, чтобы переходы не зависели от способности конкретного приложения искать слово в другом подключённом словаре.

1. Принять ZIP через существующий выбор/drag&drop/URL. Скачивание с докачкой остаётся отдельной стадией.
2. После безопасного раскрытия определить основные базы, сокращения и ресурсы; прочитать `#NAME` и собрать граф явных `[ref dict="…"]`. Идентифицировать цели по названию словаря, а не по имени файла.
3. Показать состав пакета и связанные группы до запуска записи. По умолчанию объединить связанные базы; независимые конвертировать отдельно. Для этого архива: **PhoneticList + Universal → один MDX/MDD**, **PhraseBook → отдельный MDX/MDD**. `_abrv` используется при разборе Universal.
4. Проверять внутренние ссылки внутри своей базы, межсловарные — по указанной базе и её раскрытым ключам. Различать «база-цель отсутствует», «имя базы неоднозначно» и «статья в найденной базе отсутствует». Обрабатывать циклические зависимости без повторного импорта.
5. В объединённом результате сохранить все статьи и происхождение. При совпадении ключей включать содержимое обеих баз с явными названиями источников; не перезаписывать одну статью другой. Обычные `entry://` ведут к ключу внутри того же результата. Совпадение ключей и точная адресация разделов требуют отдельной проверки в целевых читалках.
6. Разнести пути ресурсов по источникам и переписать обращения к ним, чтобы одинаковые имена изображений/аудио разных баз не конфликтовали. Сохранить название, описание и языки исходных баз в отчёте; разрешить пользователю изменить название объединённого результата.
7. Итоговый отчёт содержит состав пакета, связи, объединение, действительные отсутствующие цели и восстановление форматирования. Интерфейс показывает одно сообщение и «(ещё N предупреждений)», полный список остаётся в JSON.

Раздельные MDX можно оставить дополнительным режимом для пользователей, которым важно исходное разделение. Он должен сообщать о внешних зависимостях, а не выдавать их за отсутствующие локальные статьи. Нельзя обещать одинаковое поведение межфайловых переходов во всех читалках. Например, GoldenDict отдельно преобразует `entry://` в собственную схему поиска: [исходный код обработчика MDX](https://github.com/goldendict/goldendict/blob/master/mdx.cc#L1046).

## Что подтвердить при реализации

Минимальные проверки: две связанные базы; отсутствующая/неоднозначная база; циклическая связь; два одинаковых ключа без потери статей; совпадающие имена ресурсов; автоподключение `_abrv`; перекрывающиеся теги без потери текста; отмена анализа/объединения; повтор после перезапуска; этот архив как локальная пользовательская проверка без включения содержимого в Git. Переходы объединённого результата следует проверить минимум в GoldenDict-ng и независимой MDict-совместимой читалке. Текущая проба не является такой приёмкой.
