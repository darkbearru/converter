# Локальный конвертер DSL → MDX/MDD

Дата: 18 октября 2026 года. Статус: одобрена пользователем, включая отдельное отображение прогресса скачивания и конвертации.

Пользователь одобрил эту спецификацию в чате после добавления Windows, сборок iOS/Android, импорта по ссылке с восстановлением загрузки и явного требования отдельных индикаторов прогресса. Следующий этап — подготовка и просмотр плана реализации с выбором способа выполнения.

## 1. Назначение и результат

Создать приложение на Tauri 2 + Vue 3, которое преобразует словарные базы Lingvo DSL в словари MDict: `.mdx` со статьями и `.mdd` с изображениями, озвучкой и оформлением. Источник выбирается в файловой системе или задаётся ссылкой. Здесь MDX означает бинарный формат MDict.

Пользователь устанавливает готовое приложение. Для конвертации ему не требуются PHP, Python, Node.js, Rust или сервер. Инструменты разработки нужны только для сборки исходников. Все вычисления и рабочие данные остаются на устройстве. Интернет требуется для скачивания источника по ссылке; выбранные локальные и уже полностью скачанные файлы конвертируются без сети.

Основные платформы первой версии — macOS и Windows. Тот же проект должен поддерживать сборки iOS и Android с работающим основным сценарием: выбор локального источника или скачивание по ссылке → конвертация → экспорт MDX/MDD. Мобильная поддержка включает файловый доступ и адаптацию интерфейса, а не только наличие конфигурации сборки.

Новые входные форматы добавляет разработчик: реализует модуль читателя, регистрирует его и пересобирает приложение. Загружаемые пользователем плагины в первую версию не входят.

## 3. Пользовательский сценарий

1. Пользователь выбирает локальные словари и ресурсы либо вводит ссылку на `.dsl`, `.dsl.dz` или ZIP. На macOS и Windows доступно также перетаскивание файлов. При необходимости отдельно задаётся ссылка на ZIP с ресурсами.
2. Для источника по ссылке сначала скачиваются все файлы задания. Видны полученные байты, общий размер при наличии, скорость и действия «Приостановить», «Продолжить», «Отменить». После сбоя доступно продолжение загрузки.
3. Только после полного получения файлов приложение определяет формат, кодировку, название и языки, показывает состав источника и проблемы. Локальные файлы переходят к этому этапу сразу.
4. Пользователь при необходимости меняет кодировку, название и расположение результата, назначает ресурсы. Действие «Скачать и конвертировать» автоматически продолжает обработку с заранее заданными параметрами; если требуется выбор словаря в ZIP или устранение неоднозначности, задание ожидает ввода пользователя.
5. Конвертация выполняется в фоне относительно интерфейса. Отображаются этап, обработанный объём, число статей и ресурсов, предупреждения и кнопка отмены. Ни одна часть словаря не конвертируется параллельно с его незавершённым скачиванием.
6. После записи и проверки пользователь получает MDX, MDD и отчёт. MDD включает стандартное оформление и доступные исходные ресурсы. Результат можно открыть в папке на macOS/Windows или сохранить через системный диалог на мобильной платформе.

Очередь показывает состояния каждого словаря отдельно. Ошибка одного задания не отменяет остальные. Все исходные файлы доступны только для чтения; конвертер не изменяет и не удаляет их.

## 4. Входные словари и упаковка

### 4.1. DSL

Поддержать:

- `.dsl` и `.dsl.dz`; сжатый поток читается последовательно, без требования произвольного доступа к DictZip;
- UTF-8 с BOM и без него, UTF-16LE/BE с BOM и Windows-1251;
- LF и CRLF; заголовочные директивы `#NAME`, `#INDEX_LANGUAGE`, `#CONTENTS_LANGUAGE`;
- несколько заголовков одной статьи, экранирование, комментарии и значимые отступы;
- варианты заголовков с необязательными и несортируемыми частями, подстановку `~`;
- подстатьи с `@`, ссылки между статьями, изображения и звук;
- соседний словарь сокращений `_abrv.dsl` или его сжатый вариант, если он передан вместе с основной базой.

Кодировка определяется сначала по BOM, затем строгой проверкой UTF-8. Для данных без BOM, не являющихся корректным UTF-8, предлагается Windows-1251 с явным указанием выбранной кодировки. Для UTF-16 без BOM и других неоднозначных источников пользователь может выбрать кодировку вручную. Некорректные последовательности не заменяются незаметно символом `�`.

Рендерер DSL преобразует как минимум `[b]`, `[i]`, `[u]`, `[c]`, `[m]`/`[mN]`, `[p]`, `[trn]`, `[ex]`, `[com]`, `[sup]`, `[sub]`, `[t]`, `[lang]`, `[ref]`, `[url]`, `[s]` и `<<…>>`. Вложенность и экранирование разбираются парсером. Неизвестные теги сохраняются как видимый экранированный маркер вместе с содержимым и добавляют предупреждение; произвольный исходный HTML не исполняется.

Несортируемые части исключаются из ключа поиска, но сохраняются в отображаемом заголовке. Необязательные части дают отдельные варианты ключа. Варианты одной статьи используют одно содержимое на уровне промежуточной модели; необходимость повторения тела в бинарном результате определяется форматом записи. Число вариантов одной статьи ограничено, превышение даёт диагностическую ошибку вместо неконтролируемого разрастания.

Подстатья доступна как отдельный поисковый ключ и сохраняет связь с основной статьёй. Одинаковые заголовки разных статей не перезаписывают друг друга: все статьи сохраняются в исходном относительном порядке внутри группы совпадающих ключей.

### 4.2. Ресурсы и ZIP

На macOS и Windows пользователь может передать папку ресурсов или ZIP с ресурсами. На всех платформах доступен локальный или скачанный ZIP-пакет с `.dsl`/`.dsl.dz`, словарём сокращений и ресурсами с сохранением относительных путей. ZIP является транспортной упаковкой; читателем словарного формата остаётся DSL-модуль.

Если ZIP содержит несколько основных словарей, приложение перечисляет их до запуска. Для каждого создаётся отдельное задание; принадлежность ресурсов определяется относительно расположения словаря в пакете и может быть уточнена пользователем. Вложенные ZIP не распаковываются рекурсивно. Зашифрованные ZIP и другие архивные контейнеры в первую версию не входят.

Пути ресурсов разрешаются внутри явно выбранных источников. Сначала проверяется точное совпадение; резервное сопоставление по регистру или Unicode-нормализации допустимо только при единственном кандидате и отражается в отчёте. Неоднозначные совпадения являются ошибкой. Нельзя выходить за корень источника через `..`, абсолютный путь или символическую ссылку.

Ресурс копируется в MDD один раз на уникальный логический путь. Две разные последовательности байтов с одним выходным ключом являются ошибкой. Отсутствующий ресурс даёт предупреждение, видимую текстовую отметку в статье и итоговый статус «Готово с предупреждениями».

При ZIP-импорте действуют лимиты количества файлов, размера распакованных данных и коэффициента распаковки. Файлы извлекаются потоково в отдельную рабочую директорию задания; архивные пути и ссылки проверяются до записи. Логические имена ресурсов отделены от физических имён: локальные временные файлы получают внутренние идентификаторы. Это сохраняет имена ключей MDD, даже если архив содержит допустимое логическое имя, которое зарезервировано или неудобно для файловой системы Windows.

### 4.3. Источник по ссылке и восстановление загрузки

Поддержать прямые HTTP/HTTPS-ссылки на `.dsl`, `.dsl.dz` и ZIP, включая ссылки с query-параметрами и обычные HTTP-перенаправления. Расширение в URL не обязательно: после скачивания формат проверяется по содержимому. Ссылка на HTML-страницу, форму входа или страницу облачного обменника не считается ссылкой на словарь; её содержимое не передаётся в DSL-парсер. Авторизация через браузер, обход страниц, cookies и подключение аккаунтов хранилищ в первую версию не входят.

Ресурсы поступают в одном ZIP со словарём, из явно добавленного ZIP по второй ссылке либо из выбранных локальных источников. Приложение не пытается угадывать адреса соседних файлов на сервере. Все удалённые источники конкретного задания должны завершить загрузку и проверку до анализа и конвертации. Полностью полученный источник можно конвертировать повторно без повторного скачивания, пока он сохранён в локальном кэше.

Загрузчик на Rust пишет поток в собственное постоянное хранилище приложения: файл `<source-id>.part` и отдельный манифест. Имя на сервере служит только подсказкой отображаемого имени; оно не определяет путь записи. Манифест содержит исходный и конечный URL, полученные валидаторы, известный полный размер, подтверждённое смещение, хеши подтверждённых порций и состояние загрузки. Запись контрольной точки выполняется после сохранения соответствующих байтов; манифест заменяется атомарно. После сбоя хвост за последней подтверждённой точкой отбрасывается, а сохранённые порции проверяются перед продолжением.

Пауза, сетевой сбой и закрытие приложения сохраняют подтверждённые байты. После перезапуска незавершённая загрузка показывается как приостановленная и возобновляется действием «Продолжить». Автоматические сетевые повторы во время активного задания допускают до трёх попыток с увеличением задержки; ожидание можно прервать. После исчерпания попыток данные сохраняются, а задание предлагает повтор. Пауза или ожидание пользователя не блокируют остальные задания очереди.

Для докачки выбран следующий алгоритм:

- Запрос задаёт `Accept-Encoding: identity`; автоматическая HTTP-декомпрессия отключена, чтобы смещения относились к сохраняемым байтам. Сжатый `.dsl.dz` при этом остаётся сжатым файлом. Неожиданное HTTP-кодирование ответа не дописывается в существующую часть и возвращает диагностическую ошибку.
- Продолжение использует `Range` с подтверждённого смещения и `If-Range` с сохранённым сильным ETag того же конечного ресурса. Слабый ETag и одна только дата изменения не считаются достаточными для склейки.
- Байты дописываются только при корректном `206`: начальная позиция `Content-Range` совпадает со смещением, полный размер согласован, валидатор не противоречит сохранённому. Некорректный диапазон останавливает попытку без дописывания.
- Ответ `200` на продолжение, изменившийся ресурс или отсутствие сильного валидатора переводят загрузку в получение с нуля. `416` также вызывает повторную полную загрузку: совпадение размеров само по себе не подтверждает готовность.
- Если сервер не поддерживает безопасную докачку, приложение показывает причину повторного скачивания. Нельзя объединять части разных версий файла.

Семантика диапазонов и условных запросов основана на [RFC 9110, разделах 13.1.5 и 14](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.5). HEAD-запрос не является обязательным условием загрузки: сервер может предоставлять нужные сведения только при GET.

Завершение загрузки требует успешного окончания HTTP-потока и совпадения известной длины. Вычисляется SHA-256 полного локального файла; если пользователь указал ожидаемую SHA-256, она должна совпасть. Собственный хеш без эталона служит контролем последующего локального хранения, а не подтверждением подлинности источника. При неизвестном размере показываются байты и скорость без вымышленного процента. После проверки состояния файла и формата `.part` публикуется как завершённый локальный источник; только тогда разрешён переход к конвертации.

Прерванные загрузки хранятся отдельно от временных файлов конвертации и не удаляются при обычной очистке незавершённых заданий. Пользователь может удалить принадлежащую приложению загрузку или кэш явным действием. Отмена задания останавливает текущую передачу, сохраняет её подтверждённую часть для возможного повтора и не выдаёт неполный файл за готовый источник.

HTTP-клиент работает в нативном слое, не зависит от CORS WebView, проверяет TLS-сертификаты для HTTPS и не выполняет автоматический переход с HTTPS на HTTP. Ограничены количество перенаправлений, ожидание соединения и простои чтения; длительность успешной передачи большого файла не ограничивается коротким общим таймаутом. Контролируются свободное место и предельный размер источника, включая ответы без `Content-Length`. Ошибки HTTP, истёкшая ссылка и повторный запуск представлены в интерфейсе отдельно от ошибок DSL.

Полные URL могут содержать токены, поэтому сохраняются только в приватном манифесте загрузки. Публичный отчёт и журнал содержат идентификатор источника и имя узла, без полного URL и query-параметров. Замена истёкшей ссылки создаёт новый источник; перенос неподтверждённых частей между произвольными URL в первую версию не входит.

## 5. Архитектура и границы модулей

```text
Vue: локальный источник/URL, настройки, очередь, прогресс, отчёт
                    │ команды и события Tauri
                    ▼
Оболочка: диспетчер заданий, загрузчик с докачкой, хранилище
                    │ локальные подготовленные источники
                    ▼
Rust core: реестр читателей → DSL → общая модель словаря
                                      │
                          временные данные и сортировка
                                      │
                                MDX/MDD writer
                                      │
                           проверка → результат → экспорт
```

### 5.1. Интерфейс Vue

Интерфейс отвечает за выбор локальных данных или ввод URL, настройку задания и отображение состояния скачивания и конвертации. Он получает метаданные и небольшие сообщения о ходе работы. Содержимое словарей, архивы и ресурсы не пересылаются целиком через JavaScript/IPC.

Тяжёлая работа выполняется вне UI-потока. Диспетчер ограничивает частоту сообщений прогресса; журнал и список диагностик читаются порциями, не накапливаются без ограничений в Vue.

### 5.2. Оболочка Tauri и платформенное хранилище

`PlatformStorage` предоставляет импорт источников, рабочую директорию, проверку доступного места и экспорт готовых файлов. Непрозрачные дескрипторы источников принадлежат оболочке. Ядро не принимает `content://`, iOS security-scoped URL или команды нативных диалогов.

Оболочка подготавливает локальные читаемые источники для ядра. На macOS это выбранные файлы с действующим разрешением доступа; на мобильных устройствах — контролируемые локальные копии. При копировании используется потоковый нативный доступ. Полученный от Android провайдера URI нельзя передавать в обычный `std::fs::File::open` как путь.

На Windows используются выбранные файлы и директории с корректной обработкой Unicode-путей, разделителей, зарезервированных имён и блокировок файлов. Перед публикацией результата дескрипторы записи закрываются. На обеих настольных платформах относительные пути из архива проверяются независимо от синтаксиса путей текущей ОС.

`SourceDownloader` — отдельный Rust-модуль подготовки источников. Он не зависит от WebView и парсера DSL, получает URL, локальное место хранения, сохранённую контрольную точку и команды управления, возвращает полностью полученный источник и события передачи. Диспетчер сохраняет связь «задание → источники», проверяет завершённость всех загрузок и только затем вызывает ядро конвертации. Повтор после ошибки конвертации использует уже готовую локальную копию. Сетевые функции не входят в контракт `DictionaryReader`.

Для работы с системными документами используются официальные плагины Tauri и узкий платформенный мост для операций, которых нет в их публичном API. Мост не содержит логики DSL или MDX. Tauri документирует [мобильные плагины на Swift/Kotlin](https://v2.tauri.app/develop/plugins/develop-mobile/); стандартный диалог возвращает разные формы URI на iOS и Android, что учитывается в [API выбора файлов](https://v2.tauri.app/reference/javascript/dialog/).

### 5.3. Независимое Rust-ядро

Ядро располагается в отдельном crate без зависимости от Tauri, WebView, Swift и Kotlin. Его можно проверять обычными Rust-тестами. Оно принимает подготовленные источники, параметры, сигнал отмены и получатель сообщений прогресса.

Основные единицы:

| Модуль | Ответственность |
| --- | --- |
| `formats` | Реестр форматов, описание возможностей и ограниченная проверка содержимого |
| `dsl` | Декодирование, разбор DSL, построение статей и HTML |
| `model` | Метаданные, статьи, ресурсы и диагностика |
| `pipeline` | Этапы конвертации, отмена, временные данные и внешняя сортировка |
| `mdict` | Бинарная запись MDX и MDD |
| `validation` | Структурная проверка готового результата |

Каждый модуль зависит от контрактов модели, а не от внутренностей другого читателя.

### 5.4. Контракт нового входного формата

`DictionaryReader` предоставляет описание формата, `probe`, `inspect` и последовательное чтение статей в переданный приёмник. `probe` работает на ограниченном префиксе и метаданных источника; расширение файла служит подсказкой, а не единственным доказательством формата. `inspect` не требует загрузки всего словаря.

Читатель получает доступ только к источникам текущего задания. Он возвращает общие метаданные, статьи с подготовленным безопасным HTML, ссылки на ресурсы и диагностику. Специфичный для DSL разбор тегов остаётся в DSL-модуле.

При добавлении формата разработчик:

1. Создаёт модуль и реализует `DictionaryReader`.
2. Добавляет запись в реестр и тестовые примеры.
3. Проверяет контракт на общих тестах читателей.
4. Пересобирает приложение.

Список форматов и фильтры в интерфейсе формируются из реестра. Запись MDX/MDD, очередь и платформенное хранилище при этом не меняются. В первой версии реальный поддерживаемый формат один — DSL; расширяемость дополнительно проверяется тестовым читателем, не отображаемым пользователю.

## 6. Промежуточная модель и сохранение смысла

- `DictionaryMetadata`: название, описание, языки, исходная кодировка, идентификатор входного формата.
- `DictionaryEntry`: стабильный идентификатор статьи, исходная позиция, поисковые ключи, отображаемый заголовок, HTML и ссылки на ресурсы.
- `ResourceDescriptor`: логический относительный путь, тип содержимого, размер при наличии и дескриптор потокового чтения.
- `Diagnostic`: машинный код, серьёзность, этап, статья/строка/ресурс и русское сообщение.

Порядок сортировки не изменяет исходное написание заголовков. HTML экранирует текст и атрибуты, сохраняет переносы, абзацы и поддерживаемую семантику DSL. Внутренние переходы и озвучка формируются в соглашениях MDict; ресурсы получают согласованные ключи в MDD. Стандартное оформление поставляется в `converter.css` внутри MDD и подключается из статей; пользователь не обязан искать отдельный CSS.

Поэтому обычный успешный результат содержит оба файла, даже если исходный словарь текстовый: MDD включает стандартное оформление. Звуковые и графические файлы сохраняются побайтово. Поддержка воспроизведения конкретного медиакодека зависит от используемой программы чтения; конвертер не перекодирует исходные медиа.

Дублирующиеся статьи сохраняются отдельно. Развёрнутые варианты заголовка не создают циклических перенаправлений. Неразрешённая внутренняя ссылка сохраняет видимый текст и попадает в отчёт. Проверка ссылок выполняется по дисковому индексу ключей.

## 7. Запись MDX/MDD и большие словари

Выход первой версии — MDict v2 без шифрования, с UTF-8 для статей MDX, предусмотренным форматом кодированием ключей MDD, zlib-сжатием и контрольными суммами. Писатель создаёт заголовок, блоки ключей, их сводный индекс и блоки записей; смещения и размеры проверяются на переполнение. Нельзя получать MDX простым переименованием текстового файла.

Для основного конвейера предусматривается собственный модуль последовательной записи с дисковыми промежуточными данными. Проверенная при проектировании [реализация записи mdictlib](https://github.com/lonelam/mdictlib/blob/master/src/write/mod.rs) хранит все статьи в памяти, поэтому её builder не принимается за решение для больших баз. Библиотеку можно использовать в проверках как независимо реализованный читатель после фиксации версии.

Сортировочный ключ MDX строится приведением Unicode-символов к нижнему регистру и удалением ASCII-пунктуации и обычного пробела U+0020; для MDD применяется нижний регистр с сохранением пунктуации и пробелов. Это не локальная сортировка операционной системы и не полное Unicode case folding. Заголовки задают соответствующие параметры `KeyCaseSensitive=No` и `StripKey=Yes` для MDX, `StripKey=No` для MDD. Правило согласуется с [фиксированной сортировкой mdictlib](https://github.com/lonelam/mdictlib/blob/master/src/write/collation.rs).

Единый компаратор применяется к внешней сортировке, границам блоков и поисковому индексу. Оригинальные строки ключей сохраняются; для совпавших сортировочных ключей применяется стабильный исходный порядок. Совместимость подтверждается независимым поиском по ключам, в том числе с пунктуацией, регистром и не-ASCII символами, а не только последовательным чтением файла.

Этапы: импорт → анализ → чтение/рендеринг → сортировка → запись MDX → запись MDD → проверка → публикация результата. Для каждого этапа показывается измеримый счётчик. Если общее количество статей ещё неизвестно, отображаются прочитанные байты и статьи без выдуманного процента или ETA.

Тела статей сохраняются в дисковый spool; сортировочные записи содержат ключ, позицию и ссылку на тело. Порции сортируются в пределах бюджета и объединяются с ограниченным количеством одновременно открытых файлов. Ресурсы и выходные блоки читаются и записываются потоково. Индексы блоков также могут временно храниться на диске.

Начальный бюджет буфера сортировки — 64 MiB на macOS/Windows и 16 MiB на мобильных платформах. Это бюджет одного компонента, а не обещание общего RSS приложения. Декодированное тело статьи и итоговый HTML по отдельности ограничены 8 MiB в UTF-8; превышение завершает задание с понятной ошибкой. Размеры отдельного ресурса не определяют объём его буфера: большой ресурс должен передаваться несколькими блоками.

До и во время обработки контролируются рабочий диск, лимиты архива и выделение памяти. Ошибки нехватки места и отказа провайдера документов возвращаются как структурированные ошибки. Реальные скорость и пиковая память измеряются при проверке; заранее заданных обещаний производительности нет.

## 8. Состояния, ошибки и публикация

Состояния задания: `queued`, `downloading`, `download_retry_wait`, `download_paused`, `download_failed`, `importing`, `inspecting`, `awaiting_input`, `converting`, `validating`, `publishing`, `succeeded`, `succeeded_with_warnings`, `failed`, `cancelled`, `interrupted`. У каждого удалённого источника есть собственная контрольная точка и состояние получения. Текущий этап проверки загрузки, сортировки или записи передаётся отдельным полем. Состояние экспорта мобильного результата хранится отдельно от состояния конвертации.

Переход для URL-задания: `queued → downloading → importing → inspecting → converting`. Если требуется уточнение параметров, после анализа используется `awaiting_input`. Пауза, сетевые повторы и ошибки загрузки не разрешают переход в `converting`. Статусы `download_paused` и `download_failed` позволяют продолжить получение источника, а `interrupted` после прерывания уже начатой конвертации требует повторить конвертацию с начала по готовым входным файлам.

Диагностика различает предупреждения и ошибки. Неизвестный тег или отсутствующий ресурс сохраняет читаемый контент и даёт предупреждение. Неопределимые границы статьи, повреждённый сжатый поток, неразрешимая кодировка, конфликт выходных путей и ошибки записи завершают задание. Статьи не пропускаются молча.

Отмена проверяется между сетевыми порциями, статьями, порциями распаковки, сортировки, копирования и записи блоков. Она не оставляет частичный результат со статусом «Готово». Большие операции не должны откладывать проверку отмены до конца файла. Для скачивания доступна отдельная пауза с сохранением подтверждённых байтов; возобновление конвертации с середины по этой кнопке не подразумевается.

На macOS и Windows результат сначала полностью подготавливается и проверяется во временной директории на том же томе, что выбранная папка назначения. Затем вся директория публикуется переименованием. Имя — `<имя>-converted`, при совпадении добавляется свободный числовой суффикс. Существующие пользовательские файлы не перезаписываются. В директории находятся MDX, MDD и отчёт `conversion-report.json`.

На мобильных платформах проверенные результаты хранятся в собственном хранилище приложения. Пользователь сохраняет единый ZIP с MDX, MDD и отчётом либо экспортирует файлы отдельно. Передача внешнему провайдеру документов — отдельная операция, не гарантированно атомарная. Отмена или ошибка экспорта не удаляет готовый локальный результат и позволяет повторить сохранение; интерфейс явно показывает, что сохранено.

Завершённые мобильные результаты сохраняются до удаления пользователем. При следующем запуске удаляются только временные файлы незавершённой конвертации; такие задания получают статус `interrupted` и могут быть запущены заново. Кэш полностью скачанных источников, файлы `.part` и манифесты контрольных точек сохраняются отдельно. Незавершённая загрузка переходит в `download_paused` и может быть продолжена. Автоматического продолжения с середины конвертации в первой версии нет.

Отчёт содержит версии приложения и формата, типы источников, размеры и SHA-256 скачанных файлов, число продолжений/перезапусков загрузки, параметры конвертации, счётчики исходных статей/выходных ключей/ресурсов, этапы, диагностические сообщения и итоговые файлы. Полные URL в отчёт не включаются. Большой список диагностик пишется потоково; интерфейс читает его страницами. Текст отчёта и названия тестовых сценариев — на русском, технические идентификаторы — на английском.

## 9. Основные настольные и мобильные платформы

### 9.1. macOS и Windows

Обе настольные платформы входят в основной выпуск и имеют одинаковые функции: локальный и URL-импорт, восстановление скачивания, работа с папками ресурсов, очередь, отмена, отчёт и публикация результата. Работоспособность Windows проверяется отдельно от macOS; мобильные сборки не заменяют проверку ни одной настольной платформы.

Для macOS предусмотреть `.app`/`.dmg` для Apple Silicon и сборку x86_64 для Intel. Для Windows первой версии выбрать Windows 10 22H2 и Windows 11, x64, Rust target `x86_64-pc-windows-msvc`; ARM64 Windows в эту версию не входит.

Основной установщик Windows — NSIS `-setup.exe`. Для установки без сети он включает офлайн-установщик WebView2 (`webviewInstallMode: offlineInstaller`); наличие PHP/Python/Node.js у пользователя не требуется. Поддержка этого режима описана в [Tauri Windows Installer](https://v2.tauri.app/distribute/windows-installer/#offline-installer). Уже установленный подходящий WebView2 используется повторно.

Сборка и проверка Windows выполняются на Windows-машине, VM или Windows CI: нужны Rust MSVC, Microsoft C++ Build Tools, Node.js и зависимости упаковки Tauri. Кросс-компиляция на macOS не считается заменой проверки установки и запуска. Требования среды описаны в [Tauri Prerequisites для Windows](https://v2.tauri.app/start/prerequisites/#windows). Подпись дистрибутива настраивается отдельно с ключами вне Git.

### 9.2. Общая мобильная часть

Один Vue-интерфейс адаптируется к небольшому экрану: последовательные шаги импорта, настройки, выполнения и результата; учёт safe area и сенсорного управления. Основные действия доступны без перетаскивания и без ввода абсолютных путей.

Локальный мобильный импорт выполняется через системный выбор документов; также доступен ввод URL и общий загрузчик с восстановлением. Для словаря с множеством вложенных ресурсов предпочтителен один ZIP. Выбор одиночного DSL также поддерживается; недостающие ресурсы можно добавить ZIP-пакетом. Нельзя предполагать доступ к соседним файлам только потому, что выбран DSL.

Скачивание и конвертация работают, пока приложение открыто на переднем плане. После остановки процесса системой незавершённая конвертация получает `interrupted`, а загрузка — `download_paused` с сохранённой контрольной точкой. Работа после закрытия приложения, background service, автозапуск и гарантированное завершение при блокировке экрана в первую версию не входят. Очередь, контрольные точки загрузок и доступные результаты не зависят от сохранения процесса в памяти.

### 9.3. iOS

Предусмотреть сборку для устройства `aarch64-apple-ios` и симулятора Apple Silicon `aarch64-apple-ios-sim`. Минимальная версия приложения — iOS 15 как проектное решение. Для сборки нужны macOS, полный Xcode, соответствующие Rust targets и мобильные зависимости Tauri; это требования среды разработчика, перечисленные в [Tauri Prerequisites](https://v2.tauri.app/start/prerequisites/#ios).

Импортированные документы копируются в рабочее хранилище до запуска ядра. Экспорт выполняется системным сохранением документа. Разрешения на внешние документы не трактуются как бессрочные пути. Проект включает необходимые декларации приватности для используемых файловых API; требования указаны в [Tauri File System](https://v2.tauri.app/plugin/file-system/#ios).

Сборка для симулятора и распространение на устройствах учитываются отдельно. Подписанный архив для установки и распространения требует идентификатора приложения и настроенной подписи/provisioning. Подпись и публикация описываются в инструкции сборки, но выпуск в App Store не является частью этой задачи. См. [Tauri iOS Code Signing](https://v2.tauri.app/distribute/sign/ios/).

### 9.4. Android

Предусмотреть ARM64-сборку для устройства и x86_64-сборку для эмулятора. Поддержку 32-битных ABI в первую версию не включать. Минимальная версия приложения — Android 10/API 29 как проектное решение; это не утверждение о минимуме Tauri.

Импорт и экспорт используют системный Storage Access Framework. `content://` остаётся дескриптором провайдера; нативный слой последовательно копирует данные в рабочее хранилище и из него. Широкое разрешение на управление всем хранилищем не требуется. При отмене выбора, отозванном доступе или недоступном документе возвращается понятное состояние. Основа поведения — [Android: доступ к документам](https://developer.android.com/training/data-storage/shared/documents-files).

Для скачивания объявляется разрешение `android.permission.INTERNET`. Сетевой клиент и его TLS-зависимости должны собираться для обеих выбранных Android ABI; сетевой сценарий проверяется в установленном приложении, включая потерю сети и продолжение после перезапуска.

Для сборки нужны JDK, Android SDK/NDK и Rust targets. Предусмотреть APK для установки и AAB как формат сборки для дальнейшего распространения; релизная подпись хранится вне Git. Форматы и команды описаны в [Tauri Google Play](https://v2.tauri.app/distribute/google-play/). Публикация в Google Play не входит в задачу.

## 10. Интерфейс и настройки

Основной экран macOS/Windows содержит действия «Добавить файлы» и «Добавить по ссылке», очередь и панель параметров выбранного задания. Для URL показываются этап скачивания, байты, скорость, состояние восстановления и действия паузы/повтора. После получения источника отображаются этап и счётчики конвертации. Экран результата показывает файлы, предупреждения и действия сохранения/открытия результата. На мобильном экране те же операции идут последовательными шагами.

Настройки первой версии: локальный источник или URL, необязательная ссылка на ZIP ресурсов и ожидаемая SHA-256 загрузки, кодировка «Авто»/ручная, название и описание словаря, выбор связанных ресурсов, папка результата на macOS/Windows. Распознаваемые языки переносятся из метаданных. Настройки сжатия, редактирование статей и конструктор тем пользователю не предлагаются.

Для каждого задания отображаются два независимых блока прогресса: **«Скачивание»** и **«Конвертация»**. Переход к конвертации не сбрасывает и не переименовывает индикатор скачивания: остаются видны его завершение и полученный объём. Для локального источника в первом блоке указано «Локальный файл».

В блоке скачивания показываются прогресс каждого удалённого файла, суммарные полученные байты, известный полный объём, скорость и состояние паузы/докачки. Процент отдельного файла вычисляется только при известном размере; общий процент задания — только при известных размерах всех его удалённых файлов. При неизвестном размере используется неопределённый индикатор с фактическими байтами. После перезапуска восстанавливаются подтверждённые счётчики; перезапуск скачивания изменившегося файла явно обозначается.

В блоке конвертации показываются текущий этап и его прогресс: байты чтения, статьи, сортируемые/записанные ключи либо ресурсы — в зависимости от этапа. Процент этапа доступен только при известном знаменателе. Единый процент всей конвертации не вычисляется из произвольных весов этапов. Счётчики и результат завершённых этапов сохраняются для отчёта; предупреждения не маскируются под ошибку прогресса.

События содержат идентификатор задания, идентификатор текущего запуска и последовательный номер. Старые события предыдущего запуска не могут откатить состояние после паузы, повтора или завершения. Промежуточные обновления ограничены частотой 5 раз в секунду; переходы состояний и последнее событие отправляются сразу. Индикаторы имеют текстовые значения и доступные подписи, не зависят только от цвета.

Базовое оформление статей поставляется вместе с приложением. Полноценный словарный браузер, редактор и предварительный просмотр произвольного исходного HTML в первую версию не входят. Содержимое диагностик отображается как текст.

## 11. Проверка и критерии приёмки

### 11.1. Семантика и формат

- Небольшие контролируемые DSL-примеры покрывают все заявленные кодировки, CRLF/LF, BOM, вложенные теги, экранирование, комментарии, варианты заголовков, подстатьи, сокращения и ссылки.
- Примеры с PNG/JPEG и аудиофайлами подтверждают точное содержимое ресурсов и доступность по ссылкам из статей.
- Отдельные проверки сохраняют все дублирующиеся статьи, различают число исходных статей и выходных ключей, не теряют кириллицу, CJK и дополнительные Unicode-символы.
- Независимый MDX/MDD-ридер проверяет заголовки, контрольные суммы, все ключи и записи на небольших примерах, поиск и извлечение ресурсов. Поиск охватывает первый/последний ключ и границы блоков, регистр и пунктуацию.
- Проверка результата самим писателем или только парным собственным ридером недостаточна. Дополнительно полученный словарь открывается в независимом приложении чтения MDict; фиксируются программа, версия и проверенные статьи/ресурсы.
- При предоставлении пользователем реальных DSL выполняются конвертация и сопоставление счётчиков, характерных статей и ресурсов. Без таких файлов подтверждённое покрытие ограничивается контролируемыми примерами, что отражается в отчёте проверки.

### 11.2. Отказоустойчивость и большие данные

- Отмена на импорте, сортировке, записи и проверке не публикует частичный результат.
- Повреждённый DSL/DZ/ZIP, неизвестный тег, отсутствующий ресурс, коллизия путей, нехватка места и ошибка экспорта дают ожидаемую диагностику.
- ZIP с выходом за рабочую директорию, символическими ссылками или превышением лимита отклоняется.
- Сгенерированный крупный словарь превышает бюджет сортировки и запускает несколько проходов объединения; объём данных и число записей фиксируются вместе с временем и пиковым RSS. Полного массива статей/ресурсов в памяти не возникает.
- Большой одиночный ресурс превышает размер буфера записи и проверяется по хешу после извлечения из MDD.
- Перезапуск после прерывания корректно различает готовые результаты и незавершённые задания. Повторный экспорт не запускает конвертацию заново.

### 11.3. Скачивание и восстановление

- Управляемый локальный HTTP-сервер выдаёт известный файл и имитирует обрыв, таймаут, перенаправление, ответы с диапазонами и без них. Эти тесты не зависят от доступности стороннего сервиса.
- После обрыва, паузы и перезапуска приложения докачивается только недостающий диапазон при неизменном сильном ETag. Итоговые размер и SHA-256 совпадают с исходным файлом.
- Изменение ETag, ответ `200` вместо `206`, слабый/отсутствующий ETag и `416` вызывают корректный перезапуск; фрагменты разных версий не склеиваются. Неверное начало `Content-Range`, несогласованный размер и ответ короче объявленной длины либо с незавершённым HTTP-фреймингом не принимаются за готовый файл.
- Повреждённая сохранённая порция и лишний хвост после сбоя выявляются при проверке контрольной точки. Ошибка записи на диск не отмечает несохранённые байты как подтверждённые.
- Скачивание проверяется при неизвестном `Content-Length`, отключённой HTTP-декомпрессии, `.dsl.dz`, ZIP, редиректе на CDN, URL без расширения и URL с query-параметрами. HTML-страница входа не попадает в конвертацию.
- Сетевые повторы ограничены; пауза, отмена и исчерпание попыток сохраняют контрольную точку. Полные URL и токены не появляются в публичном отчёте или журнале.
- Задание со словарём и отдельным архивом ресурсов не запускает конвертацию до завершения обеих загрузок. После успешного получения файлов конвертация работает при отключённой сети; её повтор не скачивает источник заново.
- Очистка временных файлов конвертации не удаляет частичную загрузку. На мобильной платформе восстановление проверяется после остановки процесса, на настольной — после закрытия и повторного запуска приложения.
- Индикаторы скачивания и конвертации проверяются отдельно: переход между этапами, несколько файлов с неизвестным размером одного из них, пауза/докачка, перезапуск изменённого файла и позднее событие старого запуска. Для неизвестного объёма не показывается выдуманный процент; готовность скачивания не означает готовность конвертации.

### 11.4. Платформенная матрица

| Платформа | Артефакт/проверка | Основной сценарий |
| --- | --- | --- |
| macOS Apple Silicon | `.app` и `.dmg`, запуск на macOS | Локальный/URL DSL/DZ/ZIP, докачка, очередь, отмена, результат |
| macOS Intel | Сборка x86_64 и инструкция; runtime проверяется при наличии среды | Общее ядро и интерфейс |
| Windows x64 | NSIS `.exe`, установка и запуск на Windows 10/11; офлайн-проверка WebView2 | Локальный/URL DSL/DZ/ZIP, докачка, Unicode-пути, очередь, отмена, результат |
| iOS | Сборка и запуск в симуляторе; конфигурация устройства и подписи | Импорт ZIP/DSL/URL, докачка, конвертация, сохранение результата, прерывание |
| Android | APK ARM64 и APK x86_64 для эмулятора, возможность AAB | SAF/URL-импорт, докачка, конвертация, экспорт, отмена, прерывание |

Проверки компиляции, установки, запуска, реального устройства и релизной подписи фиксируются раздельно. Поддержка Windows или мобильной сборки не объявляется проверенной по одному наличию файлов проекта. Если Windows-среда, SDK, симулятор или подпись отсутствуют, в результате указывается конкретная непроведённая проверка; готовность macOS не подменяет проверки Windows и мобильных платформ.

## 12. Границы первой версии и порядок поставки

В состав первой версии входят ядро DSL → MDX/MDD, интерфейс и рабочие сборки macOS/Windows, локальный и URL-импорт с восстановлением загрузки, общий реестр читателей, переносимая обработка файлов, мобильный интерфейс, конфигурации и рабочие сценарии iOS/Android. macOS и Windows принимаются как основные платформы; мобильные сборки используют то же ядро и принимаются по отдельным сценариям из матрицы.

Следующие функции отложены: другие реальные входные форматы, обратная конвертация MDX → DSL, слияние словарей, редактирование статей, загружаемые плагины, шифрование выходных словарей, перекодирование медиа, облачная синхронизация и публикация в магазинах.

Репозиторий должен содержать исходники, контролируемые примеры и документацию запуска/сборки четырёх платформ. В инструкции явно разделяются требования разработчика и отсутствие языковых runtime-зависимостей у пользователя. Секреты подписи, URL с токенами, кэш загрузок, большие сгенерированные базы и пользовательские словари не входят в исходники.

Подробный [план реализации](../plans/2026-10-18-converter-implementation.md) определяет файлы, последовательность задач и проверки. Он начинается с совместимости бинарного результата, восстановления загрузки и переносимости файлового доступа, затем связывает их с интерфейсом. Работающий внешний вид сам по себе не считается готовым конвертером.

## 13. Источники проектных решений

- [dict2mdx](https://github.com/sobaee/dict2mdx): исходный аналог пользователя; Python-конвертация и упаковка MDD.
- [php-multiconverter](https://github.com/dictz/php-multiconverter): второй аналог пользователя; в корне доступны архив и README со ссылкой на [проект dictz](https://github.com/dictz/dictz.github.io).
- [Tauri Architecture](https://v2.tauri.app/concept/architecture/): разделение нативного приложения и WebView.
- [Tauri CLI](https://v2.tauri.app/reference/cli/): команды сборок macOS, Windows, iOS и Android.
- [Tauri Windows Installer](https://v2.tauri.app/distribute/windows-installer/): установщик Windows и офлайн-поставка WebView2.
- [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html): условные HTTP-запросы и диапазоны для докачки.
- [mdictlib](https://github.com/lonelam/mdictlib): независимая реализация MDict на Rust и явно задокументированное ограничение текущего writer по памяти.

Ссылки на аналоги используются для исследования поведения и совместимости; их исходники не являются автоматически выбранной основой нового приложения. Сторонние зависимости фиксируются в lock-файлах и используются с соблюдением их лицензий.
