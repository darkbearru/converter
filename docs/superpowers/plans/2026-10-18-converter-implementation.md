# Converter Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Выпустить локальный DSL → MDX/MDD конвертер для macOS/Windows с восстановлением скачивания, отдельными прогрессами и функциональными сборками iOS/Android.

**Architecture:** Независимое Rust-ядро конвертирует подготовленные локальные источники; отдельная библиотека скачивает их с контрольными точками. Tauri связывает обе библиотеки, платформенное хранилище и очередь с адаптивным Vue-интерфейсом. Конвертация начинается после полного получения всех источников задания.

**Tech Stack:** Tauri 2, Vue 3, TypeScript, Vite; Rust; Tokio/reqwest с rustls, flate2 с Rust-backend, encoding_rs, ZIP, serde, SHA-256; Vitest, Vue Test Utils, Playwright; Swift/Kotlin только для мобильного доступа к документам.

**Spec:** [Одобренная спецификация](../specs/2026-10-18-dsl-mdx-converter-design.md). Этот файл — входная точка; четыре связанных плана составляют один объём реализации.

## Global Constraints

- Основные платформы первой версии — macOS и Windows.
- Первый входной формат: `.dsl`, `.dsl.dz`; ZIP — транспортная упаковка.
- Выход — незашифрованные MDict v2 `.mdx` и `.mdd`, стандартный `converter.css` входит в MDD.
- Пользователю не требуются PHP, Python, Node.js, Rust или сервер; локальная конвертация работает без сети.
- Новые форматы добавляет разработчик через `DictionaryReader` и пересборку.
- Очередь; одна активная конвертация. Пауза загрузки и ожидание ввода не блокируют остальные задания.
- Отдельные индикаторы скачивания и конвертации для каждого задания.
- Промежуточные обновления ограничены частотой 5 раз в секунду; переходы состояний и последнее событие отправляются сразу.
- Начальный бюджет буфера сортировки — 64 MiB на macOS/Windows и 16 MiB на мобильных платформах.
- Декодированное тело статьи и итоговый HTML по отдельности ограничены 8 MiB в UTF-8.
- Windows 10 22H2/Windows 11 x64; iOS 15; Android 10/API 29, ARM64 и x86_64.
- Русские интерфейс, ошибки, комментарии и названия тестов; технические идентификаторы — на английском.
- Не менять исходники словарей, не перезаписывать пользовательские результаты, не включать словари/кэш/секреты/URL с токенами в Git.
- Планы содержат будущие проверки, а не результаты уже выполненных сборок.

## Review Focus

1. Сбой между записью байтов и контрольной точки: сохраняется только подтверждённый префикс; тест B1.
2. Разрыв UTF-16/CRLF/DSL-токена на границе буфера: статьи и номера строк не меняются; тест A3.
3. Позднее событие отменённого запуска: готовый результат и два прогресса не откатываются; тесты C1/C2.
4. ZIP с Unicode-коллизиями и именами Windows `CON`/`AUX`: логические ресурсы не теряются и не перезаписываются; тест A2.
5. Один большой ресурс и большое число блоков: запись остаётся потоковой, независимый ридер получает исходные байты; тесты A1/A5.

## Состояние проекта и среды на момент планирования

Репозиторий содержит только спецификацию и эти планы; реализации, пакетов и тестов пока нет. План выполняется из корня репозитория. Пути в таблицах ниже относятся к этому корню; это запланированные файлы.

В текущей macOS-среде проверены Node.js `24.18.0`, npm `12.2.0`, Rust/Cargo `1.72.1`, единственный Rust target `aarch64-apple-darwin`. Выбран `/Library/Developer/CommandLineTools`, полный Xcode этим не подтверждён; `xcodebuild -version` не выполняется. В стандартных местах не найдены Android Studio и Android SDK. Windows-среда ещё не проверялась.

При выполнении A1 установить совместимый стабильный Rust отдельно от глобального default и зафиксировать полученную точную версию в `rust-toolchain.toml`. Минимум официального dialog-плагина на дату планирования — Rust 1.90; проверить также MSRV выбранных зависимостей. `Cargo.lock` и `package-lock.json` фиксируют фактически разрешённые версии. SDK/подпись требуются на соответствующих платформенных этапах, не для написания документов.

| Проверки | `crates/*/tests/`, `tests/ui/`, `docs/validation/` | Библиотечные, frontend и нативные сценарии |

`converter-core` не зависит от Tauri, сети и мобильных API. `converter-download` не зависит от DSL или core. CLI и `converter-app` используют обе библиотеки; Tauri вызывает application service, DTO которого преобразуют разные события в состояние задания. Мобильный мост используется через `PlatformStorage`, не через парсер.

## Проверки на границах поставки

После A: `cargo test --locked -p converter-core -p converter-cli`, CLI-конвертация и открытие результата независимым MDict-приложением. После B: `cargo test --locked -p converter-download -p converter-cli` и обрыв/докачка с управляемым сервером. После C: `npm run typecheck`, `npm test -- --run`, `npm run test:e2e`, библиотечные тесты и настоящие `.app`/Windows installer smoke-сценарии. После D: сборка и запуск iOS simulator и Android emulator, матрица из спецификации.

В рамках каждого этапа проверять только изменённый компонент и его потребителей. Общий прогон проводится на интеграционных границах и перед итоговым ревью, а не после каждого небольшого правочного коммита. Если нет Windows/SDK/подписи или реального DSL, записать конкретную непроведённую проверку; не подменять её браузерным mock или самим наличием конфигурации.

Документы `docs/validation/*` сохраняют команды, версии, входы, ожидаемые и фактические результаты, а для больших данных — размер, время и пиковый RSS. Синтетические большие входы генерируются вне Git. Реальные словари добавляются в проверку только после предоставления пользователем; их отсутствие не блокирует контролируемые fixtures.

## Рекомендуемый способ выполнения

Рекомендую **Native**: последовательная реализация в этом чате с отдельным итоговым независимым ревью. Контракты reader/writer, контрольных точек и очереди тесно связаны; одному исполнителю проще удерживать их согласованными. Альтернатива — **Subagent-driven**, с отдельным исполнителем и ревьюером для каждой задачи, затем ревью всей ветки.

Перед реализацией пользователь просматривает четыре связанных плана и выбирает способ выполнения. При Native применяется `superpowers:executing-plans`, при Subagent-driven — `superpowers:subagent-driven-development`. Имеющийся checkout можно использовать, если он остаётся чистым; необходимость изоляции определяется при начале исполнения через `superpowers:using-git-worktrees`, а не созданием worktree на этапе написания плана.

## Источники для реализации

- [reqwest](https://docs.rs/reqwest/latest/reqwest/): нативный потоковый HTTP; отключить автоматическую распаковку, выбрать rustls.
- [encoding_rs](https://docs.rs/encoding_rs/latest/encoding_rs/) и [flate2](https://docs.rs/flate2/latest/flate2/): декодирование и сжатые потоки.
- [Tauri Dialog](https://v2.tauri.app/plugin/dialog/) и [Mobile Plugins](https://v2.tauri.app/develop/plugins/develop-mobile/): граница файлового доступа.
- [Tauri WebDriver](https://v2.tauri.app/develop/tests/webdriver/): браузерные проверки и нативный запуск учитываются раздельно. Прямой `tauri-driver` поддерживает Windows/Linux; на macOS возможен embedded WebDriver через `@wdio/tauri-service`. Ручной native smoke остаётся проверкой системных диалогов и packaged release.
